# Browser workspace and generator compatibility

## Current architecture

- The Ruby DSL is evaluated once into `Mobilis::System`. There is no generic
  handler-stack dispatcher: native `Manifest#materialize`, constrained
  `Manifest#materialize_static`, browser topology/inspector projections, and
  serialization are separate consumers of the same system model. This is the
  existing multi-environment seam and should not be replaced by another DSL.
- The browser owns one persistent official CRuby/WASM VM. Ruby owns the active
  source snapshot, Prism-based transformations, the last valid system model,
  Haml rendering, and semantic event handlers. Selection and embedded-document
  staging remain browser-only and do not invoke Ruby.
- `SourceDocument` rewrites only Prism-located literal ranges. Embedded archive
  commits check a SHA-256 parent revision, repack through the shared
  `Mobilis::EmbeddedArchive` codec, replace one payload range, and revalidate
  before committing the source transaction.
- Browser generation uses the real `Manifest#materialize_static` and service
  writers against the writable in-memory WASI filesystem. `Browser::Generator`
  then snapshots generated bytes into Ruby state for inspection/download. That
  WASI tree is currently ephemeral and is not the browser workspace.
- The native Rails writer invokes the Rails builder container, Bundler, Git,
  and post-generation commands. The browser application artifact currently
  contains no Rails gems; `rails/generators` cannot be required. Rails remains
  authorable but its writer is correctly marked local-only.
- The production app is static nginx. The official Ruby runtime and the
  independently packaged Ruby application are integrity-checked before the VM
  is instantiated. No backend or continuously running Ruby work exists.

## Filesystem boundary

Use `isomorphic-git` with LightningFS, both pinned and locally bundled, for a
persistent IndexedDB working tree and ordinary `.git` directory. Upstream
documents that LightningFS is the maintained browser adapter and warns that
callers should flush after Git operations because writes may otherwise be
reordered around a crash.

The persistent working tree is authoritative for versioned files:

- `/workspace/mobilis.rb` is the actual Ruby DSL source.
- generated files are written below `/workspace/generate/` only after a real
  successful Mobilis generation.
- `.mobilis/last-valid.rb` is untracked browser recovery metadata, not project
  authority.

The WASI filesystem remains Ruby's synchronous execution scratch space. A
narrow bridge copies source into Ruby before evaluation and copies successful
generator results into the persistent workspace. This avoids pretending an
asynchronous IndexedDB filesystem is a synchronous POSIX mount. Git and Ruby
therefore share one explicit workspace contract without duplicating Mobilis
semantics or replacing existing `File`-based writers.

Source input is persisted even while invalid. A separate last-valid snapshot
allows reload to preserve invalid text while retaining a meaningful visual
projection. Visual and embedded edits first pass the existing atomic Ruby
transaction, then update `mobilis.rb`. No-op writes compare bytes and do not
touch the working tree.

Revision restore is guarded by staged/unstaged status and staged embedded edits.
It flushes pending writes, snapshots the prior revision, restores the requested
tree without moving the branch head, refreshes Ruby/UI from the restored DSL,
and rolls back to the prior tree if the filesystem or refresh transaction
fails. The restored tree remains visible as ordinary changes that can be
reviewed and committed.

## Git slice

The first browser slice now supports local initialization, status matrix,
textual diff, stage-all, commit, log, and safe revision restore. Source and real
generator output persist across reloads. Remote operations are deliberately
absent. Git operations run only on explicit browser actions and flush
LightningFS before reporting success.

The Git UI is a Haml-rendered workspace shell with a small JavaScript controller
because the Git library and IndexedDB filesystem are asynchronous browser APIs.
It does not parse, validate, or transform Mobilis source. Ruby remains the only
semantic authority.

## Rails generator investigation

The isolated probe pins railties 8.1.4.1 and invokes the public
`Rails::Generators::AppGenerator.start` API with matched options. Native CRuby
produces the complete 44-file minimal application without a Rails executable,
Bundler, Git, or Docker. The same gem sources load far enough in the official
`@ruby/4.0-wasm-wasi` 2.10.1 runtime to create the initial application tree.

Two platform findings are explicit:

- Rails/Thor calls `chmod`; the existing Mobilis WASI adapter safely ignores
  only `ENOSYS`/`ENOTSUP`, allowing generation to continue.
- ActiveSupport then requires `bigdecimal` while generating the master key and
  encrypted credentials. The standard runtime does not contain that native
  extension, and a host `.so` cannot be loaded by WASM. The probe exits nonzero
  at this exact point and partial files are not treated as success.

The native Rails writer is unchanged and remains the production path. No Rails
templates are copied or approximated for the browser.

## Capture and shim slices

Introduce a separate `Mobilis::GeneratorCapture` entry point. Each definition
names a fixture and exact argv/environment, clones the fixture into a fresh
temporary directory, executes once, and records provenance plus created,
modified, deleted, and mode changes in deterministic JSON. Failed commands are
captured as failures and rejected as compatibility evidence.

Argument variations always restore the same baseline and compare capture
deltas. The initial corpus targets the real `rspec:install` Rails ecosystem
generator. Evidence is separate from `GeneratorCompatibility` shim code.

The first shim declares exact generator/gem versions and accepted arguments,
validates expected files before changes, applies through a small filesystem
interface, refuses unexpected existing content, and is tested against the
capture corpus. Real generators remain preferred wherever supported.

## Verification plan

1. Persistent valid and invalid reload, no-op writes, generated-file
   persistence, and one-VM lifecycle are covered in Playwright.
2. Git init/status/stage/commit/log/diff/dirty protection/revision restore and
   Ruby UI refresh are covered in Playwright.
3. Direct native and actual WASM Rails generator probes with matched versions,
   structured file comparison, and an explicit compatibility matrix.
4. Reproducible real baseline/variation captures and isolated temporary roots.
5. Corpus-derived shim success, unsupported arguments, input conflicts, and
   repeated application behavior.
