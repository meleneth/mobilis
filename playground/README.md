# Mobilis Browser Playground

The playground is a static browser application. CRuby runs through ruby.wasm;
Ruby owns application state, Prism analysis, Haml rendering, DOM event handling,
and Mobilis execution. Turbo Streams apply targeted updates. JavaScript only
boots WASM and Turbo, renders Ruby-derived architecture through Mermaid, and
provides browser filesystem, local Git, download, and ZIP primitives.

## Run

```sh
docker compose up --build
```

Open <http://localhost:8080>. The runtime image is nginx; it does not contain a
Ruby server, Ruby interpreter, or generation API. At startup the browser loads
the pinned official Ruby WASM interpreter from jsDelivr and the independently
hosted Mobilis application artifact from nginx. Once those assets load,
authored source stays local and generation requires no outbound requests.

For a host build, run `npm ci`, install the isolated `playground/Gemfile`, and
run `playground/scripts/build`. Serve `playground/public/` over HTTP; browsers
do not allow the WASM application to boot reliably from `file://` URLs.

For development without a CDN request, explicitly publish the package's exact
pinned interpreter beside the other static assets:

```sh
RUBY_WASM_RUNTIME_URL=/vendor/ruby+stdlib.wasm \
COPY_LOCAL_RUBY_WASM=1 \
playground/scripts/build
```

`LOCAL_RUBY_WASM_PUBLIC_PATH` changes the copied public path when needed.
`MOBILIS_APPLICATION_MANIFEST_URL` can point at another compatible manifest.
There is no automatic fallback between CDN, local, or stale versions.

## Runtime and application delivery

The interpreter and Ruby application have independent ownership:

- `@ruby/4.0-wasm-wasi` 2.10.1 supplies the official CRuby 4.0 full runtime.
  Production configuration names the version-pinned jsDelivr URL and records
  the expected byte size, SHA-256, and Fetch integrity value. The browser
  verifies the bytes before compilation.
- The build stages Mobilis, the playground Ruby/Haml source, templates, and the
  pure-Ruby Haml, Temple, Thor, and Tilt libraries into a deterministic ustar
  archive. It preserves the normal filesystem layout and `$LOAD_PATH`; Ruby
  continues to use ordinary `require` calls.
- `mobilis-app-manifest.json` records the content-addressed artifact URL,
  application identity, compatible runtime package/version, load paths, boot
  feature, and every member's size and SHA-256. The browser validates the tar
  header, safe paths, archive integrity, exact member set, and member hashes
  before mounting it in the writable WASI filesystem.
- The mutable runtime configuration and application manifest use `no-store`.
  The pinned runtime and content-addressed application archive are immutable
  cache entries. nginx compresses the application archive in transit.

JavaScript instantiates exactly one `RubyVM` per page session. Repeated editor
operations invoke the already loaded Ruby application; they do not reload
Mobilis or recreate the VM. `window.MobilisRuntimeDiagnostics` reports phase,
VM count, artifact identities, and fetch/verification, compilation, hydration,
instantiation, and Ruby load timings. The existing on-screen Ruby counter
continues to report semantic operation latency.

The runtime remains on the main browser thread because the current Ruby
application intentionally renders Haml/Turbo updates and binds DOM events
through the `js` bridge. Moving it to a Worker would require a new DOM protocol,
not an artifact-delivery change. The VM is resident but idle: there is no Ruby
polling or scheduled workload.

## Persistent local workspace

The browser keeps `/workspace/mobilis.rb`, real generated files below
`/workspace/generate/`, and an ordinary `.git` repository in IndexedDB through
LightningFS. The UI exposes status, textual diffs, stage-all, commit history,
and safe revision restore. The initial DSL is committed automatically; later
source and generated files change the working tree until explicitly staged and
committed. Remote Git operations are not implemented.

Invalid Ruby is still persisted exactly. `.mobilis/last-valid.rb` is ignored
recovery metadata used only to restore the last valid visual projection after
a reload; it never replaces `mobilis.rb` as authority. Revision restore is
rejected while the working tree or an embedded-document edit is dirty. Ruby
must validate the restored source before the UI accepts it, and a failure rolls
the filesystem back to its prior revision.

Git and IndexedDB are asynchronous browser APIs, while Mobilis writers expect
synchronous Ruby `File` APIs. The existing writable WASI filesystem therefore
remains generation scratch space. After successful generation, the bridge
publishes exact generated bytes into IndexedDB with an atomic directory swap.
No JavaScript implementation of Mobilis generation exists.

CDN availability is required for a cold production load. Offline behavior is
not claimed, and no service worker or silent stale-version fallback is used.
The CDN executable is version-pinned and integrity-checked, but user-authored
Ruby still has every browser capability explicitly exposed through the JS
bridge; WASM is not a complete sandbox.

## Deploy to Devastation

From a clean, committed working tree, build, push, and roll out the playground
to the local Devastation Kubernetes cluster with:

```sh
./deploy-devastation.sh
```

The script tags the image with the current commit, pushes it to
`registry.deva.station`, updates only the `mobilis/mobilis` Deployment, and
waits for the rollout. `REGISTRY`, `KUBE_CONTEXT`, `NAMESPACE`, `DEPLOYMENT`,
`CONTAINER`, and `ROLLOUT_TIMEOUT` may be overridden through the environment.

## Authoring and local generation

All DSL service methods discovered in `Mobilis::DSL::DSLContext` appear in the
builder, including Rails. The editor uses `Mobilis::DSL.generate`, so the exact
downloaded `mobilis.rb` is executable in a Mobilis checkout:

```sh
bundle install
bundle exec ruby mobilis.rb
```

The “Local bundle” download also contains `mobilis-system.json`, accepted by
the repository's existing CLI:

```sh
bundle exec mobilis generate mobilis-system.json
```

Both native paths write `generate/` and may invoke Docker. The browser replaces
only the root `generate` method token with `build` in a temporary Prism-located
evaluation copy. It never changes the source being authored or downloaded.

## Generation capabilities

Browser generation capability belongs to the realized service writer. The
base writer is filesystem-only and browser-compatible. The Rails writer marks
itself local-only because its real implementation invokes Docker, `rails new`,
Bundler, and Rails generators. A declared `run_command` is also local-only.

All current non-Rails service writers use Ruby filesystem/template emission and
are eligible for browser generation. This includes PostgreSQL, MySQL, Redis,
S3 storage, observability services, Rack, Flask, FastAPI, Go HTTP, Envoy,
Grafbase, Kafka, Google Pub/Sub, GoAWS, Cassandra, Airflow, and pgAdmin. Runtime
tests prove PostgreSQL generation; eligibility does not imply that every
possible plugin/model combination has been exhaustively tested in WASM.

Mixed projects are all-or-nothing. If any realized writer is local-only, the UI
keeps full authoring and export support but refuses browser generation. It does
not omit the incompatible service or display a partial project as complete.

## Live architecture

The architecture panel is derived from the last successfully evaluated
`Mobilis::System`. It includes explicit `connect` and `route` dependencies plus
Mobilis reference slots such as a Rails primary database, Alloy's Loki target,
and pgAdmin databases. Ruby assigns deterministic safe diagram identifiers and
escapes labels; Mermaid is only the SVG renderer and never parses or changes
the DSL.

Valid source edits and visual edits replace the diagram through the same
Turbo-driven application state. Invalid Ruby stays byte-for-byte intact while
the last valid diagram remains visible with a stale marker. Selecting a node
focuses the corresponding direct builder declaration when one exists and
selects its Prism-located Ruby source range. Services created through nested or
dynamic Ruby expressions remain visible in the diagram but may not have a
safe source declaration to navigate to.

## Service inspector

Selecting a builder card or Mermaid node opens the same service inspector and
selects the declaration's Prism range without evaluating Ruby. Direct literal
constructor properties and `connect`/`route` declarations have surgical form
controls. Incoming relationships remain read-only at the target because their
source declaration is owned by the originating service. Mobilis reference
slots and realized `depends_on` edges are displayed separately from semantic
connections.

The inspector always exposes the complete validated node JSON and a source
navigation action. Service-specific block APIs, dynamic expressions, and
properties without an established literal rewrite are intentionally edited in
the authoritative Ruby pane; the playground does not synthesize lossy controls
for them.

## Embedded documents

A service can carry a versioned Base64 tar bundle in ordinary valid Ruby:

```ruby
rack("api") do |service|
  service.embedded_archive("application-files", payload: "...")
end
```

The shared `Mobilis::EmbeddedArchive` codec emits deterministic ustar archives
with a `.mobilis-archive.json` manifest, sorted paths, normalized metadata,
SHA-256 integrity records, an optional entrypoint, and dependency metadata.
Only regular files with safe relative paths are accepted. Encoded/decoded,
entry-count, and per-file limits are enforced; links and special tar entries
are rejected.

The inspector lists recognized bundles. Opening and typing in a text member is
browser-only staged state. Save performs one Ruby request that checks the parent
source revision, repacks through the shared codec, replaces only the payload's
Prism range, and validates the complete DSL before committing. The operation is
undoable. Binary members are preserved and visible in the tree but not opened
as text.

## Source invariants

- Valid source evaluates to the real `Mobilis::System` model.
- Prism locations identify direct service declarations and literal properties.
- Visual changes replace only the relevant source range.
- Comments, whitespace, and unrelated expressions stay byte-for-byte intact.
- Invalid source remains in the editor while the last valid visual model stays
  visible.
- Dynamic names and properties remain intact and their unsafe visual controls
  are disabled.
- Arbitrary Ruby remains more expressive than the visual form; unsupported
  expressions are shown as such rather than normalized away.

## Security and responsiveness

Ruby DSL source is executable code. WASM removes normal host process and network
APIs, but it is not a complete security boundary: code can consume CPU/memory
and interact with browser APIs exposed by the application. Do not paste
untrusted source. There is no telemetry and source is never submitted.

The static server's Content Security Policy permits both `unsafe-eval` and
`wasm-unsafe-eval`. The ruby.wasm `js` bridge uses JavaScript evaluation during
initialization; allowing only WebAssembly evaluation prevents the runtime from
booting. This CSP is another reason the playground must not be treated as a
security boundary for untrusted Ruby.

Generation currently runs in the main Ruby VM. The existing writers are short,
synchronous filesystem emitters, and keeping one VM avoids duplicating the
semantic model across a worker protocol. A worker becomes appropriate if
measured generation latency becomes interactive; request IDs already prevent a
stale generation result from replacing a newer one. Long-running native
subprocess generators are intentionally local-only.

The browser owns the event loop and Ruby has no polling or scheduled workload.
An on-screen counter records semantic Ruby invocations and elapsed time.
Selection, scrolling, graph navigation, archive browsing, and staged archive
typing do not cross the Ruby bridge. A dedicated worker was not introduced:
the current Ruby application directly renders Haml/Turbo updates and measured
operations are synchronous and short; moving that VM would require a new DOM
render protocol without improving idle behavior.

## Compatibility findings

- The pinned official CRuby 4.0/WASI full runtime loads Mobilis and its
  standard-library dependencies. Mobilis, Haml, Temple, Thor, and Tilt sources
  are assembled into a deterministic, independently versioned application
  archive and loaded into a writable in-memory WASI filesystem; no custom
  CRuby compilation is required.
- Prism is a CRuby 4.0 default extension in that runtime; parsing and source
  locations execute inside WASM.
- Haml 6.4, Temple, and Tilt are pure Ruby and render components in WASM.
- Active Support's inflector is loaded lazily by the local-only Rails resource
  plugin. This avoids cross-compiling its unrelated native dependency graph.
- `git` is now loaded lazily only by native materialization. The static path
  does not load or emulate it.
- The browser entrypoint omits the unrelated JobesWar terminal demo requires
  from the historical combined native loader; Mobilis implementation files are
  otherwise loaded from the canonical require list.
- Rails application scaffolding is incompatible by design because the existing
  writer uses host subprocesses and Docker.
- WASI does not preserve POSIX executable bits. The browser filesystem adapter
  ignores only unsupported `chmod` calls while retaining the exact generated
  file bytes; native generation continues to set executable permissions.
- Application artifacts can contain only Ruby and ordinary data assets. A new
  dependency with a native extension must already be provided by the pinned
  interpreter or requires an explicit runtime compatibility decision; it
  cannot be added to the application tar as if it were pure Ruby.
